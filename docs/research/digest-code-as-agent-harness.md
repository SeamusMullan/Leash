# Digest: "Code as Agent Harness: Toward Executable, Verifiable, and Stateful Agent Systems"

arXiv 2605.18747v1 (Ning et al., UIUC / Meta / Stanford, May 2026). Source: `scratchpad/papers/2605.18747v1.txt`.

## 1. Thesis and definitions

A survey and position paper. Its thesis: code is no longer only an LLM's output but "an executable, inspectable, and stateful medium through which agents reason, act, observe feedback, and verify progress", a view it names *code as agent harness* (§1).

Definition (§1): "An agent harness refers to the software layer that surrounds an LLM with tools, APIs, sandboxes, memory, validators, permission boundaries, execution loops, and feedback channels, thereby turning a stateless model into a functional agent capable of long-running task execution."

Three coupled elements (§1): (a) model-internal capabilities (reasoning, perception, planning, simulation, evaluation); (b) system-provided harness infrastructure, "predefined tools, APIs, sandboxes, memory systems, validators, permission boundaries, telemetry, and workflows", which is "the main focus of harness engineering"; (c) agent-initiated code artifacts, "regression tests, temporary tools, DSL programs, executable workflows, reusable skills, and intermediate program states" that agents "create, execute, observe, revise, persist, and share within the task execution loop".

Distinctions. Model versus harness: "The model provides judgment: it decomposes goals, selects actions, interprets feedback, and decides when to revise"; the harness exposes tools, persists and compacts state, constrains actions through permission tiers, routes feedback, and verifies each state transition (§3). Prompt, context, and harness engineering: "prompt engineering changes instructions and context engineering changes what evidence is presented to the model, [AHE] treats the operating environment itself as the object of analysis" (§3.5). "Scaffold" is a near-synonym for harness. Frameworks and SDKs "packag[e] tools, sessions, guardrails, handoffs, workspaces, and execution environments into reusable harness components" (§3.3). Agent-authored code sits inside the harness but does not replace it.

"Code" means executable or machine-checkable artifacts (§2): programs, scripts, formal specifications, proof scripts, API schemas, tool definitions, tests, repositories, simulators, configuration files, and traces or logs of executable systems. Perception, physical state, human intent, and latent model reasoning are not code. Code qualifies through three properties, executable ("the harness can verify what the model intended"), inspectable ("failures can be diagnosed and fed back"), and stateful ("interaction history is not lost between steps"); the conclusion adds governed.

## 2. Taxonomy

**Harness Interface** (§2). *Code for Reasoning*: program-delegated reasoning; formal verification and symbolic reasoning interfaces; iterative code-grounded reasoning. *Code for Acting*: grounded skill selection; programmatic policy generation; lifelong code-based agents. *Code for Environment*: structured world representations; execution-trace world modeling; code-grounded evaluation environments; verifiable environment construction.

**Harness Mechanisms** (§3), "five interacting categories". *Planning*: linear decomposition, structure-grounded, search-based, orchestration-based (feedback-centered, staged-workflow, controller-centric). *Memory and Context Engineering*: working, semantic, experiential, long-term, multi-agent memory, plus cross-cutting context compaction and state offloading. *Tool Use*: function-oriented, environment-interaction, verification-driven, workflow-orchestration, with a lifecycle of pre-use and post-use hooks. *Harness Control via the Plan–Execute–Verify (PEV) loop*: planning as contract formation; sandboxed execution and permissioned state transition (tiers read-only, sandbox-edit, full-access); verification through deterministic sensors. *Agentic Harness Engineering (AHE)*: deep telemetry, the Evolution Agent, governed harness mutation. It also adopts the layer split "orchestration, working state, execution substrates, evaluation harnesses, observability, and governance".

**Scaling the Harness** (§4). *Roles*: program synthesis, program understanding, verification, execution, planning agents, plus meta-roles (EvoMAC's Gradient and Updating agents). *Interaction modes*: collaborative synthesis, critique-and-repair, adversarial validation, reasoning debate. *Topologies*: pre-defined heuristic (chain/waterfall, cyclic, hierarchical, star) and objective-driven adaptive (dynamic agent-pool scaling, feedback-driven DAG restructuring, runtime self-reorganization). *Execution feedback types*: compiler/syntax, test pass/fail, fuzzer crash traces, static-analysis warnings, performance profiling, fine-grained simulation feedback. *Synchronization*: sequential handoff, shared blackboard, parallel branches with merge, structured context scheduling, hierarchical memory, agent-pool scaling, revert. *Shared harness representation*: implicit/file-only, repository-based, execution-based, blackboard/shared-state. *Convergence*: correctness (test-gated), security, performance, score-based, consensus, implicit.

Domains (§5.1): code assistants, GUI/OS agents, embodied agents, scientific discovery, personalization.

## 3. Primitives and operations

Collected across §3–§5, the operations the paper names are:

*Tool lifecycle.* Expose typed tool schemas; register tools (MCP registries); pre-use hooks that run permission checks, policy rules, and argument validation, block risky commands, or open a human-in-the-loop (HITL) gate; execute inside a sandbox; post-use hooks that sanitize outputs, compact large logs, offload traces to durable storage, update memory, and trigger follow-up verification.

*Planning.* Decompose intent into ordered steps; persist the plan as a filesystem object (PLAN.md style) that can be reloaded, updated, verified, versioned in Git, and consumed by subagents across context resets; build a plan graph by dependency analysis and change-impact propagation; branch over candidate trajectories, expand, prune, and backtrack (tree search, MCTS); detect dead ends and switch to the next candidate plan; adaptive commitment (follow, revise, or abandon a plan). Contract formation: identify relevant files, expected invariants, validation commands, rollback points, risky operations, the allowed read and edit sets, and completion criteria.

*Memory and context.* Per observation, decide whether it stays in active context, is compacted into a provenance-preserving summary, or is offloaded to external storage with a retrievable handle; budgeted memory slots; structure-aware retrieval (AST chunking, iterative query rewriting, reranking); write gates and quality filtering for stored experience; consolidation of overlapping memories; context reset with a targeted progress summary (L2MAC); per-role filtered views (MetaGPT); promotion of successful snippets into a skill library. A compacted failing-test report keeps "the failing test name, key stack frames, suspected files, and links to the full log".

*Execution.* Isolated filesystem, dependency state, shell, runtime, browser/IDE, resource limits; snapshots, warm pools, resumable sessions; replay of the same patch, command, seed, lockfile, or test configuration; permission tiers; approval prompts; audit logs; gateway routing, budgets, fallbacks, cost logs.

*Verification.* Run deterministic sensors (linters, parsers, compilers, type checkers, unit/integration/regression tests, static analyzers, fuzzers, runtime monitors, CI) producing pass/fail, diagnostics, failing traces, coverage gaps, security warnings, resource limits, timeouts, policy violations. On failure choose: continue, revise a localized patch, request more context, route to another agent, reduce permissions, escalate to a human, or abandon the branch. Terminate when required checks pass, when attempts stop improving state, when the risk tier changes, or when human review is required; bounded iteration budgets; revert to a never-overwritten initial artifact (QualityFlow); attach an evidence bundle to each accepted action.

*Multi-agent.* Spawn child or worker agents dynamically (per file, or recursively by subtask complexity); handoff and delegation; parallel branches merged at a planner; blackboard reads and writes mediated by a control unit; majority vote; role-reversal clarifying questions; failure attribution followed by prompt and DAG rewriting; measuring belief-state divergence |Bk − Sk|.

*Harness engineering.* Collect telemetry; diagnose; propose revisions ("rewriting tool descriptions, changing context packing rules, adding a linter, modifying retry limits, or inserting a HITL gate"); evaluate on held-out tasks or replayed traces; promote only non-regressing changes; change contracts; canary deployment; rollback.

*Proposed, not yet common (see §7).* Per-action read and write sets, assumptions, verifier obligations, and conflict policy; semantic merge and dependency-aware locking; grounding contracts binding an action to perceptual evidence; predicted-versus-observed state comparison; approvals stored as durable harness state that update permission rules and verification criteria.

## 4. Determinism, reproducibility, and control

The control philosophy: "reliability comes from governed state transitions, not simply from better repair prompts" (§3.4).

*LLM decisions versus code decisions.* AgentCoder's Test Executor "is a deterministic Python script (not an LLM) which cleanly separates reasoning from execution" (§4.1.1). In GUI/OS worlds "the transition function T is not learned but executed"; the policy "is best thought of as a program synthesizer ... the environment is the interpreter" (§5.1.2). Verification tools are "deterministic sensors"; critiques "should interpret sensor outputs rather than replace them"; termination is governed by verification, not model confidence. The recommended split: "using linguistic reasoning as the fast path and delegating to execution as the verification oracle only for the failure modes that require it" (§4.4).

*Reproducibility.* Sandboxes let the harness "replay the same patch, command, seed, dependency lockfile, or test configuration under comparable conditions. Without this stable substrate ... failures may reflect environment drift rather than program defects" (§3.4.3). Code-defined simulators are "forkable, diffable, version-controlled, and reproducible in ways that no learned simulator can match" (§5.1.2). Deep telemetry (§3.5.1) records prompts, context, cost, latency, tool arguments, permissions, edits, snapshots, test results, branch decisions, rejected alternatives, and human interventions so harness versions can be compared by replay.

*Boundedness and governance.* Execution is permissioned in tiers; the full-access tier (network, credentials, deployment, destructive filesystem or Git operations) requires mandatory HITL gates. Permissions "should depend not only on tool identity, but also on arguments, environment state, data sensitivity, and expected side effects" (§5.2.5). AGENTS.md guidance, MCP registries, typed schemas, and adapters "make the available actions inspectable before execution rather than discovered opportunistically during execution" (§3.4.2). Approvals become "auditable state transitions: what action was proposed, what evidence was shown, what risks were surfaced, who approved or rejected it". Formal languages serve "as executable contracts that constrain, certify, and audit agent behavior".

## 5. Failure modes and mitigations

- Hallucinated APIs: API-search and retrieval tools.
- State divergence between an agent's belief and the true program state, "invisible" in file-only systems: repository or blackboard substrates, SyncMind-style synchronization, transactional state.
- Mode collapse, where "an agent's biased tests pass its own buggy code": independent test designer (AgentCoder), test-quality checker (QualityFlow), oracle audit against the spec (CANDOR).
- Oracle inadequacy ("the agent sees a green test, but the green test is not the full specification"): a verification stack whose artifacts each declare "what it verifies, what it cannot verify, and what confidence it provides"; evidence bundles; typed feedback routing (compiler error to syntax repair, test failure to behavioral diagnosis, coverage gap to test generation).
- Implicit convergence (fixed iteration count, identical output), "the most significant gap in the field": objective convergence criteria.
- Harness-level causes: "missing repository context, brittle tool interfaces, weak validators, excessive token cost, poor retry policies, or mismatched permission boundaries"; recurring "flaky sandboxes, over-permissive tool calls, or premature termination"; agents looping between failed strategies: telemetry-driven AHE.
- Context explosion and lost local consistency: working memory, compaction, offloading. Memory noise, false retrievals, staleness: governed write gates, curated experience, consolidation.
- Silent embodied failures (an out-of-workspace grasp raises no exception): validate before actuation (AutoHarness).
- Channel losses: "tests compress semantics into pass/fail, summaries save context at the cost of detail, logs are grounded but noisy, and shared blackboards improve persistence while creating authority and consistency problems".
- Self-evolving harnesses "overfitting, weakening safety, increasing cost, hiding failures, or regressing on rare but important tasks": change contracts, held-out regression suites, canaries, rollback.
- Benchmark artifacts: solution leakage in issue text; the organicity gap (correct patches maintainers reject); step-level failure attribution only 14–53% accurate.
- Sandbox escape, secret handling, side-effect prediction: capability governors, transactional sandboxing, least privilege.
- Multimodal ambiguity ("a button may look clicked without triggering the right state transition"): predicted-versus-observed checks with declared scope and uncertainty.

## 6. Existing systems compared

*Production harnesses, SDKs, protocols.* Claude Code: "packages local terminal/IDE/browser coding into a tool-mediated loop with editing, command execution, permissions, hooks, memory, and subagents"; Anthropic's harness posts separate planning, generation, and evaluation roles. Codex and GitHub Copilot coding agent: the same loop in managed workspaces with sandboxes, branches, approvals, auditable PRs. Cursor: planner–worker coordination for many parallel agents. LangChain / DeepAgents: "planning, filesystem-backed state, context management, code execution, and subagent delegation as reusable harness components". OpenHands and its SDK: a "full PEV harness" with diffs, logs, tests, approvals. SWE-agent: formalized agent–computer interface; replayable shell. AutoGen: cited only in passing. Model Context Protocol: standardizes how harnesses expose tools, context, resources; AGENTS.md: repository-local instructions. LiteLLM: permission gateway, budgets, fallbacks. Langfuse, OpenLLMetry, Promptfoo, DeepEval: observability and evaluation harnesses. Daytona, E2B, Tensorlake, Arrakis, Capsule: sandbox substrates. Microsoft Agent Governance Toolkit, Aethelgard's capability governor, transactional sandboxing: early least-privilege primitives. LangGraph, DSPy, and CrewAI are not mentioned.

*Harness optimization.* AutoHarness: synthesizes a code harness that filters invalid actions. Meta-Harness: end-to-end search over harness code using prior code, scores, traces. Agentic Harness Engineering (Lin et al.): observability-driven evolution. Natural-Language Agent Harnesses: harness logic as editable natural language run by an Intelligent Harness Runtime. GEPA, ACE: prompt and context evolution. EvoMAC, SEW, FlowReasoner, BOAD: topology evolution. Live-SWE-agent: edits its own scaffolding at runtime (stability and rollback questions).

*Multi-agent coding systems* (weakness in parentheses). ChatDev, MetaGPT: waterfall chains, pub-sub pool (implicit state and convergence). AgentCoder: coder, test designer, deterministic executor, five-iteration cap. MapCoder: recall, plan, code, debug (implicit state). Self-Collaboration: blackboard, simulated tester (falls back after four rounds). L2MAC: persistent file store with a context-scheduling Control Unit, "the most principled blackboard". MAGIS: repository evolution memory, one developer per file. HyperAgent: planner over parallel navigators and editors. PairCoder: navigator and driver, dead-end detection. FlowGen: waterfall, TDD, Scrum compared (converges on its own tests). SoA: recursive spawning (loses global consistency). QualityFlow: quality gate, imagined execution, revert. AutoSafeCoder: CWE analysis plus fuzzing. CANDOR: three-panelist vote. MAGE: clock-edge waveform feedback. MACRO: performance convergence. SyncMind: formal belief-state divergence. Agentless, AlphaCodium, RepairAgent, AutoCodeRover, RepoCoder, CodeAgent, CodePlan: single-agent repository harnesses (see §8).

*Languages and DSLs.* Lean, Isabelle, Coq (Lean4Agent models agent workflows in Lean4); SAT/SMT (SATLM); XDL, "like LLVM IR for chemistry"; BioPlanner protocol pseudocode; behavior trees (Code-BT); NormCode's semi-formal governed interface; CodeAct (Python actions instead of JSON tool calls); SEW's BPMN, CoRE, Python, YAML workflow specs.

*Interface-layer systems* (surveyed, not compared): PoT, PAL, Chain of Code, SayCan, Code-as-Policies, Voyager, WorldCoder, CWM, SWE-smith, EnvScaler, MemGovern, MemGPT.

## 7. Proposals for a language, IR, or specification

No grammar or type system is proposed, but the paper repeatedly asks for formal, executable harness specifications:

1. **Executable harness specification.** Natural-Language Agent Harnesses treat "roles, stages, contracts, adapters, state conventions, and failure taxonomies" as an editable spec that an Intelligent Harness Runtime converts "into constrained execution steps under explicit contracts, budgets, tool interfaces, and environment state"; "the plan is not merely a document, but an executable harness specification" (§3.1.4). Controller-centric orchestration uses "typed intermediate representations, shared blackboards".
2. **Shared code-centric harness substrate** (§4.3, the paper's position): "a formal, persistent representation of the shared code state that agents can query and update", unifying the repository view (structure) and execution view (behaviour) so agents can answer "does this refactoring break APIs that external code depends on".
3. **Transactional shared program state** (§5.2.4): each action declares "its read set, write set, assumptions, version dependencies, verifier obligations, and conflict policy", with semantic merge, rollback, dependency-aware locking, and re-verification after merge (analogies: version control, databases, CRDTs, build systems).
4. **Change contracts for harness mutation** (§5.2.3): "which component is modified, which failure mode it targets, what improvement it predicts, which invariants it must preserve, which evaluation can falsify it, and how it can be rolled back"; plus "mutation operators for harness components" and "telemetry standards".
5. **Verification stack with explicit scope** and per-action evidence bundles (§5.2.2); **grounding contracts** binding actions to perceptual evidence (§5.2.6).
6. **Typed tool schemas**, permission tiers keyed on arguments and side effects, and HITL approvals as durable, auditable harness state (§3.3, §5.2.5).

## 8. Evaluation

Benchmarks named: SWE-bench (plus Pro, ++, Lancer, PatchDiff, SWE-smith), FeedbackEval, Terminal-Bench, AppWorld, AgentBench, InterCode, CRUXEval, LiveCodeBench, MBPP; GUI: MiniWoB++, WebShop, Mind2Web, WebArena, OSWorld, AndroidWorld, BrowserGym, TheAgentCompany; science: MLAgentBench, MLE-bench, ScienceAgentBench, DiscoveryBench; attribution: Who&When, AgenTracer, AgentDebug.

Recommended harness-level metrics (§5.2.1): trajectory efficiency (tool calls, tokens, edits, executions, wall-clock), verification strength (coverage, oracle diversity, false-acceptance rate), recovery ability, state consistency, safety compliance, replayability; for shared state, merge success, semantic regression rate, rollback frequency, conflict recurrence, cost of human intervention. End-task success alone conflates model capability, harness quality, tool reliability, feedback quality, and environment difficulty.

Results showing harness design matters: SWE-agent and RepairAgent show that "even with the same underlying model, repository-level repair performance can vary substantially depending on how interaction state and execution feedback are organized" (§3.2.1); "changing the scaffold around the model can change agent behavior without retraining the base model" (§3.5); AIDE's tree-search scaffold reaches "roughly three times the medal rate of the next agent" on MLE-bench; BOAD's bandit-discovered teams beat hand-designed ones; AlphaCodium's flow engineering "substantially improves" over single-shot prompting; QualityFlow's gate exits 75–84% of problems after one generator call; LLM-simulated execution reaches 98%+ precision and recall on MBPP.

## 9. Open problems

§5.2: harness-level evaluation and oracle adequacy; semantic verification beyond executable feedback ("epistemically aware" loops); self-evolving harnesses without regression; transactional shared program state and semantic conflict resolution; human-in-the-loop safety and accountability as harness state ("executable accountability"); multimodal code-harness systems (multimodal compression, grounding contracts, skills as precondition/action/postcondition triples); a "science of harness engineering" with benchmarks exposing long-horizon failures, auditable telemetry, and component-isolating metrics. Code-assistant-specific (§5.1.1): verification beyond unit tests, failure attribution, capability-based safety primitives, production-scale self-evolution with rollback, live multi-agent/human/CI synchronization, and trust calibration ("when to interrupt, when to checkpoint, when to delegate, and when to defer"). Also: when execution is necessary versus linguistic simulation.
